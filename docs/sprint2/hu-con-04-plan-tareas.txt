1. CONTEXTO
-----------
  Historia: como Contador quiero relacionar cada pago recibido de la pasarela
  con las órdenes que paga, para detectar diferencias y saber qué está
  conciliado y qué no.

  Flujo: el módulo de Pagos envía pago.recibido (o el contador importa un CSV)
  -> Contabilidad registra el pago -> se concilia contra una o varias órdenes
  -> diferencia = valor del pago - valor aplicado a las órdenes
  -> CONCILIADA (|diferencia| <= tolerancia) o PENDIENTE (diferencia visible).


2. DECISIONES DE ESTA HISTORIA (2026-10-16)
-------------------------------------------
  - El pago se concilia contra ÓRDENES (numero_orden), no contra ventas por
    vendedor: el contrato pago.recibido trae "ordenes": ["ORD-1001"]. El valor
    de una orden es la suma del valor bruto de sus ventas (venta_contable).
    (Ajuste al plan original, que ligaba el detalle a venta_id.)
  - Una conciliación por pago. Cada orden lleva su valor aplicado; si no se
    indica, se aplica su saldo pendiente. Lo aplicado a una orden, sumando todas
    las conciliaciones, no puede superar su valor: una orden se puede pagar en
    partes con varios pagos.
  - Política (D-08): diferencia = valor del pago - suma aplicada.
    |diferencia| <= tolerancia -> CONCILIADA; si no -> PENDIENTE. Tolerancia 0
    por defecto (provisional, se inyecta en los casos de uso).
  - pago.recibido es idempotente por eventId (inbox) y por referencia de la
    pasarela (UNIQUE): la misma referencia con otro eventId -> 409.
    Si el evento trae órdenes se concilia automáticamente (usuario SISTEMA); si
    las órdenes no sirven (inexistentes o sin saldo) el pago se registra igual y
    queda SIN_CONCILIAR con el motivo en la respuesta.
  - Conciliar no modifica las cuentas por pagar: el pago recibido es dinero que
    entra al marketplace; el pago al vendedor es otra historia.
  - Concurrencia: bloqueo del pago (FOR UPDATE) y de cada orden
    (pg_advisory_xact_lock, en orden) para que dos conciliaciones simultáneas
    no apliquen dos veces el mismo saldo.
  - Migración 006 (Carlos). Las de Diego en el Sprint 2 usan 007 en adelante.
  - Al quedar CONCILIADA se publica contabilidad.conciliacion.cerrada (outbox).

4. CRITERIOS DE ACEPTACIÓN (escenarios)
---------------------------------------
  - Pago de 150.000 contra órdenes de 100.000 + 50.000 -> CONCILIADA, dif. 0.
  - Pago de 95.000 contra una orden de 100.000 -> diferencia -5.000, PENDIENTE.
  - Orden inexistente -> rechazo; aplicar más del saldo de una orden -> rechazo.
  - Una orden pagada con dos pagos parciales cuadra.
  - Evento repetido -> YA_PROCESADO; referencia repetida -> 409.
  - Cada conciliación queda auditada con usuario y fecha.
